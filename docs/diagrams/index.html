GateFlow 图解

本页用图表概括 GateFlow 仓库（产品名 FlowGate）的团队工作流、架构、部署、S1 请求与计费规则、数据库设计、依赖与时间线，便于负责人和团队快速了解项目全貌。内容依据 2026 年 10 月 12 日 main 提交 7dbdd4e，以及当日的开放 issue 和 PR。

阅读顺序：A 团队流程 → B 架构与部署 → C 一次 S1 请求与计费 → D 数据库 → E 计划与门禁。每张图都沿一个方向阅读（从上到下或从左到右），虚线箭头表示回退、计划或提案。

图例
  • 计划中写在可行性计划或 issue 里，但尚未实现（例如 S3 云环境、Redis 限流）。
  • 提案写在尚未合并的 PR 或尚未批准的设计修订里，可能还会改（例如 PR #33、#18 修订 3、#26/#27 的表设计）。
  • 未标注的内容已在 main 上，或是已生效的规则。图中的虚线框和虚线箭头表示“计划中”“提案”或回退。

A 团队流程

1. 团队工作流泳道图

一个 issue 从创建到 Done 的流程，每个角色一条泳道，按计划、实现、审阅、合并、验收五个阶段自上而下。来源：.github/CONTRIBUTING.md、AGENTS.md、.agents/skills/*/SKILL.md。按 CONTRIBUTING，issue 的 owner 就是它唯一的 assignee，计划批准也由该 owner 给出。“中文审阅文档”是团队惯例（见 PR #33 正文），规则文件中没有写。

2. Issue 状态机

状态由 owner 或 coordinator 用 state:* 标签设置，主线自上而下。Done 指“以 completed 关闭，且所有约定验收都已记录”；Not planned 和 Duplicate 不算 Done，转入时须记录原因与替代 issue。验收失败时用 revert PR 或开 bug issue 阻塞 Done。来源：CONTRIBUTING.md 的 Issues 一节和 gh label list。

C 一次 S1 请求与计费

6. S1 请求时序：一次 POST /v1/messages 提案

五个阶段自上而下：检查请求、验 key 与渠道、预留（失败重试一次）、转发 SSE 并采集 usage、用新的 context 结算。alt 分支中的错误响应会结束本次调用。依据 #18 的修订 3 草稿（.local/review-18/final-18-v2.md），该修订尚未批准。

8. 预留状态机 提案

预留只会从 reserved 变为 settled 一次，靠条件更新或行锁保证。重放按 (call_id, attempt_id) 或 reservation_id 返回已记录的结果。reserve 或 settle 最终失败时留下的占用，要等 UC6（门禁之后）才回收。来源：#18 修订 3 草稿、#27。

9b. 数据库 ER：schema accounting 提案

9b. Database ER: schema accounting Proposed

Read along the relationships: wallet → reservation → the ledger entry its settlement writes. Derived from #27 and the #18 revision 3 draft: a reservation keeps the prices and caps from creation time; a ledger entry keeps call_id, attempt_id, token counts as sent (null stays null), the outcome and charged. Column names not stated in the sources, such as balance, held and status, are guesses. There is no foreign key between the two schemas; tenant_id matches by string value only.
