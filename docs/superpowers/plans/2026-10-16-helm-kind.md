# Helm and kind Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox syntax for tracking.

**Goal:** Deploy four FlowGate services with Helm and prove the complete smoke suite passes through kind ingress.

**Architecture:** One application chart references externally created Secrets and a PostgreSQL endpoint. A separate disposable kind fixture supplies PostgreSQL and ingress; AWS values reference RDS and ALB without provisioning either.

**Tech Stack:** Helm 3, Kubernetes, kind, PostgreSQL 17, Python 3.13 standard library, existing Go service images.

**Spec:** ../specs/2026-10-16-helm-kind-design.md

## Global constraints

- Base and rule commit: main de208ffb766a70706c108c98fa10e00bce37d266; writer branch feat/71-helm-kind.
- Follow issue 71 description and https://github.com/bibi45c/gateflow/issues/71#issuecomment-6185242638.
- No AWS calls, KEDA implementation, inline Secret values or unrelated service changes.
- Preserve compose smoke defaults and all existing assertions.
- Scripts use Python standard library and work on Windows, Linux and macOS.
- All commits reference issue 71. Open PR after kind evidence; never merge.

## Review focus

- A missing Secret or failed bootstrap must produce bounded, diagnosable installation failure without exposing credentials.
- A rerun or upgrade must not destroy data or race service migrations and seeds.
- Unknown ingress routes, including /metrics, must not reach gateway internals.
- Placement and shutdown settings must actually render for every relevant workload, including Jobs.
- Kubernetes smoke failures must exit nonzero while compose command construction stays compatible.

Bootstrap uses a pre-install/pre-upgrade hook against already-existing PostgreSQL and Secrets, with deadlines and cleanup policy.
